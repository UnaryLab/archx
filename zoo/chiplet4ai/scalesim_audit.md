# chiplet4ai vs SCALE-Sim: memory/bandwidth model audit

Scope: `zoo/chiplet4ai/common/performance/` and `zoo/chiplet4ai/llama/query/` checked against SCALE-Sim v3 semantics (`SCALE-Sim/scalesim/`: `systolic_compute_ws.py`, `double_buffered_scratchpad_mem.py`, `read_buffer.py`, `write_buffer.py`, `single_layer_sim.py`). Goal is a relatively accurate event-based model, not trace accuracy. Fixes land item by item; unmarked findings are still open.

Measured reference (used below): 512x512 array, 10 MiB SRAMs (bank 1024, width 16), 256 GB/s DRAM, GEMM batch=1, M=2048, K=N=8192 (`_ws_schedule` direct call):
compute 785,920 cy; output_tail_stall 393,472 cy; dram write_stall 1,167,205 cy; total stalls 1,560,933 cy (2x compute); output DRAM bandwidth 636 GiB/s.

## Correct (keep)

1. **Event decomposition.** Compute lives in `*_arr` (parallel factors, aggregates to compute_cycles once), stalls are `sequential` chains of `cycle_reference` in `*_sram`/`*_dram`. Clean, and `query_cycle_breakdown` (query/utils.py:53) decomposes exactly along it.
2. **WS fold structure and per-fold cycles.** `ceil(K/R) * ceil(N/C)` folds, `M + R + C - 2` per fold (mapping.py:406) matches SCALE-Sim's demand-matrix pipeline (fill + stream + drain skew) to within a cycle. Utilization and mapping-efficiency definitions match SCALE-Sim's (systolic_compute_ws.py:394-406).
3. **Decode-step (KV growth) machinery.** `qkt_dc` steps `n`, `av_dc` steps `k` from `prefill_seq_len` to `max_seq_len`; closed-form sums (`_range_sum`, `_ceil_sum`) over the trajectory divided by `total_steps`, multiplied back by per-step counts in `layer_dc`. Exact and cheap; the `_ceil_sum` algebra checks out.
4. **Weight DRAM traffic.** Every weight fetched exactly once (`weight_read_elements = weight_elements`, mapping.py:425): correct for weight-stationary, matches SCALE-Sim filter traffic. The weight window heuristic (`_read_active_span_cycles`) gives a near-average, sensible required bandwidth.
5. **Input DRAM refetch model.** Strip-resident reuse (one K-strip resident across the inner n-fold loop, refetch scaled by fit fraction, mapping.py:417/424) is consistent with the k-outer/n-inner fold order of `_ws_fold_infos` and SCALE-Sim's fold order; a fair analytic stand-in for SCALE-Sim's active-buffer hit tracking.
6. **Double buffering.** Active/prefetch split via `active_fraction` (default 0.5), prefetch bandwidth `min(DRAM, SRAM)` (mapping.py:349-351) mirrors SCALE-Sim's double-buffered scratchpad with DRAM-fed prefetch buffer.
7. **SRAM access bookkeeping.** SRAM writes = DRAM reads (fills x active-buffer words, node.py counts use bank/2 = active half); SRAM reads = streamed elements via the array path; energy plumbed once (array-path osram accesses carry `dynamic_energy: 0` to avoid double charging). Self-consistent.
8. **SRAM service bandwidth.** `(bank/2) * width/8` bytes/cycle equals the C words/cycle the array demands in steady state given the `bank = 2 x vector` constraint in description.py; balanced by construction, as intended.

## Wrong or inconsistent (ranked)

1. **[FIXED] Output tail stall uses the wrong window** (mapping.py:456, 465). *Fixed: the output-write service window is now steady + tail; in the reference config the stall drops 393k to 0, and stays correctly positive for undersized osram.* All osram output-write bytes are forced through only the `(C-1) * folds` drain-tail cycles. Outputs actually retire throughout the steady phase (~C/cycle, exactly what osram provides), so this manufactures `(M - C + 1) * folds` stall from nothing: measured 393k cy = 50% of compute in the reference config, in a configuration that should have ~0 SRAM output stall. Window should be steady + tail (`M + C - 2` per fold). SCALE-Sim has no such term; its ofmap stalls come only from write-buffer-full vs drain bandwidth (write_buffer.py:214).
2. **[FIXED] DRAM output writes charge every partial sum, and reads/writes are gated inconsistently** (mapping.py:410/426-428, dram() 661). *Fixed with items 3/4: DRAM output traffic is now final writes plus the non-resident fraction of partial sums, gated symmetrically for reads and writes by the loop order's output working set. Reference config: writes 537 MB to 33.5 MB, write stall 1.17M cy to 0.* `dram_output_write` = `M*N*k_folds` bytes always, while `dram_output_read` is zeroed when the output tile fits. Charging all partials to DRAM matches raw SCALE-Sim ofmap traces (it streams fold partials out through the write buffer), but contradicts this architecture's `output_adder` + osram accumulation, and contradicts the read gating in the same function. Consequence in the reference config: 1.17M cy of write stall (149% of compute) and 636 GiB/s "required" write bandwidth; with on-chip accumulation it is 0 stall and ~40 GiB/s. Pick one convention: if osram accumulates, DRAM writes = `M*N` final + spill traffic, gated like the reads.
3. **[FIXED] Input and output assume opposite loop orders.** *Fixed: `_ws_schedule` (and `gemm`/`sram`/`dram`) take `loop_order` in {'auto', 'k_outer', 'n_outer'}; input refetch and output spill traffic both derive from the chosen order's working sets, and 'auto' (default) picks the order with less DRAM traffic. Reference config picks n_outer: input refetch honestly rises to 458 MB (881k cy input stall, the real bottleneck), outputs stay on-chip.* Input refetch assumes k-outer (strip resident across n-folds); the output fit test uses the per-fold tile `M * min(C,N)` (mapping.py:416), which only bounds the accumulation working set if k is *inner*. Under the actual k-outer order the output working set between k-passes is all of `M*N` (16.8M words > 5.2M osram in the reference config, i.e. it does *not* fit even though the model says it does). Each operand is optimistic under a different schedule. Fix by fixing the loop order (k-outer to match `_ws_fold_infos`/SCALE-Sim) and deriving both from it, or by making the order a parameter.
4. **[FIXED] osram accumulate reads vanish when the output "fits"** (mapping.py:427-428 feeding sram():606). *Fixed: osram accumulate reads/writes (all partial sums) are now tracked separately from DRAM spill traffic; `sram_output_read_mapping` counts and steady-state pressure use the osram-side quantities.* Zeroing `output_read_elements` is right for DRAM spill reads but also zeroes the osram partial-sum reads (`M*N*(k_folds-1)`) that on-chip accumulation performs regardless, understating osram energy and steady-state pressure. DRAM spill reads and osram accumulate reads are different quantities and need separate variables.
5. **Each operand gets the full DRAM channel; stalls combined coarsely** (mapping.py:349-351, 466). Input/weight/output each service at `min(dram_bpc, sram_bpc)` and DRAM read stall is `max(input, weight)` on whole-GEMM aggregates. SCALE-Sim USER mode also has per-operand backing bandwidths, so this "matches SCALE-Sim", but the architecture declares a single DRAM: concurrent streams should share it (sum demand vs one channel), and aggregate max-of-totals plus summed phase stalls can double-count the same wall-clock deficit (SCALE-Sim takes the per-line max across operands instead, double_buffered_scratchpad_mem.py:279).
6. **[MOSTLY FIXED] Chunked-window bandwidth is inflated when a tile does not fit.** *Fixed: `_window_from_chunks`/`_chunk_count` removed; all SRAM/DRAM traffic windows are now the compute span, so every bandwidth factor is an honest average over compute (weight keeps its startup-span heuristic, which is near-average).* Remaining: if the figures also want a burst/peak requirement distinct from the average, that needs a deliberate definition; today "peak_required_bandwidth" in fig_2_query is just the max of per-event averages.
7. **`lm_head_dc` count mismatch.** `decode()` charges `lm_head_dc` once (llama_model.py:86), but `llama_dc_array`/`llama_array` charge `lm_head_dc_arr` once per decode step (llama_model.py:51). The lm_head GEMM runs every decode step; the `decode` branch undercounts it by `max_seq_len - prefill_seq_len`.
8. **Root event double-counts.** `llama_model` chains both `llama` and `llama_array` sequentially (llama_model.py:32-36); they are two views of the same computation, so runtime/energy at the workload root is roughly double. Harmless while queries target `llama` or `llama_array`, wrong the moment anyone aggregates the root.

## Minor / hygiene

- `_dram_bytes_per_cycle` converts a "GB/s" spec with 2^30 (GiB), a 7.4% systematic error (mapping.py:42); pick one unit end to end (metric unit says GiB/s).
- `weight_fill_stall` is ~1 cycle/fold by construction (`R*C/C = R` service vs `R-1` window): a modeling artifact, not memory pressure.
- Dead code in mapping.py from an earlier cycle-driven draft: `_ws_folds`, `_ws_phase_cycles`, `_phase_stall`, `_touch_chunked_resident` (+ its only callee `_touch_resident`), `_service_output_write`, `_drain_remaining_output` (+ `_launch_output_drain`), `_cycle_reference`; `_fit_2d_tile` in utils.py. None are called from live paths.
- `query/gemm_test.py` is stale: reads `description_8b/.../checkpoint.gt`, queries `multiplier`/`av_decode` (current: `pe`, `av_dc`), and calls `query_performance_metrics` without the required `workload`/`metrics` arguments; it cannot run.
- `query/utils.py:127` annotates `-> np.float64` without importing numpy (only safe on Python >= 3.14 lazy annotations).
- `fig_2_query.py` emits `input_dram_bandwidth`, `input_active_avg_required_bandwidth`, and `input_required_bandwidth` as three copies of the same number.

## Suggested fix order (pending your go-ahead)

1 and 2 first (they dominate: together they turn a ~786k-cycle GEMM into ~2.35M cycles), then 3/4 as one coherent loop-order + output-traffic rework, then 5/6 for the bandwidth queries, then 7/8 and hygiene.
